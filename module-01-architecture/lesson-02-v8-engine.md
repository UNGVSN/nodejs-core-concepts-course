# Module 01 / Lesson 02 — The V8 Engine

> V8 is the JavaScript engine inside Node.js, and it is far more sophisticated than most developers realize. It does not simply interpret your code — it parses it into an AST, compiles it to bytecode, profiles which functions run hot, then recompiles those functions into optimized machine code. Understanding this pipeline explains why some JavaScript patterns are fast and others are mysteriously slow.

## Learning Objectives

- Trace JavaScript source code through V8's full compilation pipeline: parsing, Ignition bytecode, TurboFan optimized code
- Explain hidden classes and how they affect property access performance
- Describe inline caching and why monomorphic call sites are faster than polymorphic ones
- Identify V8's two garbage collection strategies (Scavenge for young generation, Mark-Sweep/Mark-Compact for old generation)
- Use V8 flags to inspect bytecode, optimizations, and GC behavior in Node.js

## The Compilation Pipeline

V8 uses a multi-tier compilation strategy. Every function goes through at least two stages, and hot functions get a third, optimized pass.

### Stage 1: Parsing

V8's parser reads your JavaScript source and builds an Abstract Syntax Tree (AST). The parser is lazy — it only fully parses functions that are actually called. Functions that are defined but never invoked are pre-parsed (syntax-checked but not fully compiled).

```javascript
'use strict';

// V8 fully parses and compiles this immediately because it is called
function hot() {
  return 42;
}
hot();

// V8 pre-parses this — it checks syntax but does not generate bytecode
// until (and unless) it is actually called
function cold() {
  return 99;
}
// cold() is never called — V8 saves time by skipping full compilation
```

This matters in large applications. If you define thousands of functions at module load time but only call a fraction of them during startup, V8's lazy parsing keeps startup fast.

### Stage 2: Ignition (Bytecode Interpreter)

After parsing, V8's **Ignition** interpreter compiles the AST into bytecode — a compact, platform-independent instruction format. Ignition then executes this bytecode line by line.

You can inspect the bytecode V8 generates:

```javascript
'use strict';

// Save as bytecode-demo.js, then run:
// node --print-bytecode --print-bytecode-filter=add bytecode-demo.js

function add(a, b) {
  return a + b;
}

// Call it enough times for V8 to generate stable bytecode
for (let i = 0; i < 100; i++) {
  add(i, i + 1);
}
```

Run with `node --print-bytecode --print-bytecode-filter=add bytecode-demo.js` and you will see output like:

```
[generated bytecode for function: add]
  Ldar a1
  Add a0, [0]
  Return
```

Those three instructions — load register, add, return — are what Ignition actually executes. Bytecode is faster than re-parsing the AST every time, but slower than native machine code.

### Stage 3: TurboFan (Optimizing Compiler)

V8 profiles your code as it runs. When it detects a "hot" function — one called many times with consistent argument types — it sends that function to **TurboFan**, the optimizing compiler. TurboFan generates native machine code (x64, ARM64, etc.) specialized for the observed types.

```javascript
'use strict';

// Save as turbofan-demo.js, then run:
// node --trace-opt --trace-deopt turbofan-demo.js

function multiply(a, b) {
  return a * b;
}

// Phase 1: Warm up — Ignition collects type feedback
for (let i = 0; i < 10000; i++) {
  multiply(i, i + 1); // Always called with numbers
}
// At some point during this loop, TurboFan kicks in and
// compiles multiply() to optimized machine code for (number, number)

console.log('Check the --trace-opt output for "[optimizing] multiply"');

// Phase 2: Deoptimization trigger
// If we suddenly call multiply with a different type, TurboFan
// must "deoptimize" — throw away the optimized code and fall
// back to Ignition bytecode
multiply('hello', 'world'); // String concatenation, not multiplication!

console.log('Check --trace-deopt output for "deoptimized multiply"');
```

Run with `node --trace-opt --trace-deopt turbofan-demo.js`. You will see V8 optimize `multiply` for numeric arguments, then deoptimize when you pass strings. Deoptimization is expensive — the function falls back to slow bytecode interpretation until TurboFan can re-analyze it.

## Hidden Classes

V8 does not use hash tables for JavaScript object property access. Instead, it creates **hidden classes** (internally called Maps, not to be confused with `Map`) — structural descriptions of an object's shape. Objects with the same hidden class share the same memory layout, allowing V8 to generate fast property access code.

### How Hidden Classes Work

Every time you add a property to an object, V8 creates a new hidden class that extends the previous one. Objects created with the same sequence of property assignments share the same hidden class chain.

```javascript
'use strict';

// Both objects get the SAME hidden class because properties
// are added in the SAME order
function PointGood(x, y) {
  this.x = x; // Transition: HC0 → HC1 (adds 'x')
  this.y = y; // Transition: HC1 → HC2 (adds 'y')
}

const p1 = new PointGood(1, 2);
const p2 = new PointGood(3, 4);
// p1 and p2 share hidden class HC2 — fast property access

// These objects get DIFFERENT hidden classes because properties
// are added in DIFFERENT order
function PointBad(x, y, flip) {
  if (flip) {
    this.y = y; // HC0 → HC_A (adds 'y' first)
    this.x = x; // HC_A → HC_B (adds 'x' second)
  } else {
    this.x = x; // HC0 → HC1 (adds 'x' first)
    this.y = y; // HC1 → HC2 (adds 'y' second)
  }
}

const p3 = new PointBad(1, 2, false);
const p4 = new PointBad(3, 4, true);
// p3 and p4 have DIFFERENT hidden classes — slower property access
```

### The Performance Impact

```javascript
'use strict';

// Benchmark: consistent vs inconsistent object shapes

function createConsistent(n) {
  const arr = [];
  for (let i = 0; i < n; i++) {
    // Same property order every time → same hidden class
    arr.push({ x: i, y: i * 2, z: i * 3 });
  }
  return arr;
}

function createInconsistent(n) {
  const arr = [];
  for (let i = 0; i < n; i++) {
    const obj = {};
    // Random property order → different hidden classes
    if (i % 2 === 0) {
      obj.x = i; obj.y = i * 2; obj.z = i * 3;
    } else {
      obj.z = i * 3; obj.x = i; obj.y = i * 2;
    }
    arr.push(obj);
  }
  return arr;
}

function sumX(arr) {
  let total = 0;
  for (let i = 0; i < arr.length; i++) {
    total += arr[i].x; // Property access speed depends on hidden class stability
  }
  return total;
}

const N = 1_000_000;

console.time('consistent-create');
const consistent = createConsistent(N);
console.timeEnd('consistent-create');

console.time('inconsistent-create');
const inconsistent = createInconsistent(N);
console.timeEnd('inconsistent-create');

console.time('consistent-sum');
sumX(consistent);
console.timeEnd('consistent-sum');

console.time('inconsistent-sum');
sumX(inconsistent);
console.timeEnd('inconsistent-sum');
```

The consistent version is measurably faster because V8 generates optimized machine code that assumes a fixed memory offset for property `x`. The inconsistent version forces V8 into slower dictionary-mode lookups.

**Rule of thumb:** Initialize all properties in the constructor, always in the same order. Never add properties conditionally or after construction.

## Inline Caching

Inline caching (IC) is V8's technique for speeding up repeated property accesses and function calls. When V8 encounters `obj.x` for the first time, it looks up `x` using the hidden class. On subsequent accesses, if the object has the same hidden class, V8 skips the lookup and goes directly to the memory offset.

There are three states:

| State | Meaning | Speed |
|-------|---------|-------|
| **Monomorphic** | Always the same hidden class | Fastest — direct offset access |
| **Polymorphic** | 2-4 different hidden classes | Medium — small lookup table |
| **Megamorphic** | 5+ different hidden classes | Slowest — full hash table lookup |

```javascript
'use strict';

// Monomorphic — V8 loves this
function getX_mono(obj) {
  return obj.x;
}

// All calls use objects with the same shape
for (let i = 0; i < 10000; i++) {
  getX_mono({ x: i, y: i }); // Same hidden class every time
}

// Megamorphic — V8 cannot optimize this
function getX_mega(obj) {
  return obj.x;
}

// Each call uses a different object shape
getX_mega({ x: 1 });
getX_mega({ x: 1, y: 2 });
getX_mega({ x: 1, y: 2, z: 3 });
getX_mega({ x: 1, a: 2 });
getX_mega({ x: 1, b: 2 });
getX_mega({ x: 1, c: 2, d: 3, e: 4 });
// The IC for getX_mega is now megamorphic — every call is slow
```

You can see IC states with `node --trace-ic your-script.js 2>&1 | grep getX`. In production, you will not use these flags, but understanding IC explains why passing heterogeneous objects to a single function is slower than passing uniform objects.

## Garbage Collection

V8 uses a **generational garbage collector** based on the observation that most objects die young. The heap is divided into two generations:

### Young Generation (Scavenge)

The young generation is small (a few MB) and uses a **semi-space** algorithm called Scavenge:

1. V8 allocates new objects in the "from" space
2. When the from-space fills up, V8 pauses JavaScript execution (stop-the-world)
3. The collector scans for live objects and copies them to the "to" space
4. Dead objects are implicitly freed — they are simply left behind in the from-space
5. The from-space and to-space swap roles

Scavenge is fast (sub-millisecond) because the young generation is small and most objects are already dead.

### Old Generation (Mark-Sweep and Mark-Compact)

Objects that survive two Scavenge cycles are promoted to the old generation. This space is collected less frequently using **Mark-Sweep** (or Mark-Compact when memory is fragmented):

1. **Mark phase**: V8 traverses all reachable objects starting from GC roots (global scope, stack, handles) and marks them as alive
2. **Sweep phase**: V8 scans the heap and frees memory occupied by unmarked (dead) objects
3. **Compact phase** (optional): V8 defragments the heap by moving live objects together

Mark-Sweep pauses are longer than Scavenge pauses because the old generation is larger. V8 mitigates this with **incremental marking** (spread the mark phase across multiple event loop iterations) and **concurrent sweeping** (sweep on a background thread).

### Observing GC in Action

```javascript
'use strict';

// Run with: node --trace-gc gc-demo.js

// Force young generation collections by rapidly creating short-lived objects
function youngGenPressure() {
  console.log('\n--- Young generation pressure ---');
  for (let i = 0; i < 100_000; i++) {
    // These objects die immediately — perfect Scavenge candidates
    const temp = { a: i, b: i * 2, c: 'ephemeral' };
    // temp is unreachable after this iteration
  }
}

// Force old generation collections by holding references
function oldGenPressure() {
  console.log('\n--- Old generation pressure ---');
  const longLived = [];
  for (let i = 0; i < 500_000; i++) {
    // These objects survive because longLived holds references
    longLived.push({ data: Buffer.alloc(64), index: i });
  }
  // Now release them
  longLived.length = 0;
}

youngGenPressure();
oldGenPressure();

// Memory after cleanup
const mem = process.memoryUsage();
console.log(`\nHeap used: ${(mem.heapUsed / 1024 / 1024).toFixed(2)} MB`);
console.log(`Heap total: ${(mem.heapTotal / 1024 / 1024).toFixed(2)} MB`);
```

Run with `node --trace-gc gc-demo.js`. You will see output like:

```
[  42:0x...]  Scavenge 4.2 (8.0) -> 3.1 (8.0) MB, 0.4 / 0.0 ms ...
[  42:0x...]  Mark-Sweep 98.3 (130.0) -> 14.1 (67.0) MB, 12.3 / 0.0 ms ...
```

The Scavenge pauses are sub-millisecond. The Mark-Sweep pauses are in the tens of milliseconds — long enough to affect tail latency in a high-throughput server.

## Optimization Killers

Certain JavaScript patterns prevent TurboFan from optimizing a function. These are known as "optimization killers" or "bailouts":

| Pattern | Why It Kills Optimization |
|---------|--------------------------|
| `arguments` object manipulation | V8 cannot statically determine the arguments shape |
| `try/catch` inside hot loops | (Largely fixed in modern V8 but still adds overhead) |
| Changing object shapes after creation | Invalidates hidden classes, triggers deoptimization |
| `eval()` or `new Function()` | V8 cannot analyze dynamically generated code |
| `delete` operator on objects | Transitions object to slow "dictionary mode" |
| `with` statement | Makes scope resolution unpredictable |

```javascript
'use strict';

// BAD: delete transitions to dictionary mode
const user = { name: 'Alice', age: 30, role: 'admin' };
delete user.role; // Now user is in dictionary mode — all property access is slow

// GOOD: set to undefined instead
const userGood = { name: 'Bob', age: 25, role: 'admin' };
userGood.role = undefined; // Hidden class preserved — still fast
```

## Practical V8 Flags for Node.js

Here are the most useful V8 flags for understanding what the engine does with your code:

```javascript
'use strict';

// This file is a reference — run each flag separately

// See bytecode for a specific function
// node --print-bytecode --print-bytecode-filter=myFunc script.js

// See which functions get optimized / deoptimized
// node --trace-opt --trace-deopt script.js

// See garbage collection events
// node --trace-gc script.js

// Detailed GC statistics
// node --trace-gc-verbose script.js

// See inline cache state transitions
// node --trace-ic script.js 2>&1 | head -50

// Force a GC (useful for benchmarks, never in production)
// node --expose-gc script.js
// Then call: global.gc()

function myFunc(x) {
  return x * x + x;
}

for (let i = 0; i < 100_000; i++) {
  myFunc(i);
}

console.log('Done — check flag output for details');
```

These flags are your X-ray into V8's compilation decisions. You should never use them in production, but they are invaluable for understanding why a specific code path is slow.

## V8 Memory Layout

Understanding how V8 organizes memory helps you reason about garbage collection and memory leaks:

```
┌─────────────────────────────────────────────┐
│                  V8 Heap                     │
│                                              │
│  ┌──────────────┐  ┌────────────────────┐   │
│  │    Young      │  │       Old          │   │
│  │  Generation   │  │    Generation      │   │
│  │              │  │                    │   │
│  │ ┌──────────┐ │  │  Mark-Sweep /      │   │
│  │ │From-space│ │  │  Mark-Compact      │   │
│  │ ├──────────┤ │  │                    │   │
│  │ │ To-space │ │  │                    │   │
│  │ └──────────┘ │  └────────────────────┘   │
│  └──────────────┘                            │
│                                              │
│  ┌──────────────┐  ┌────────────────────┐   │
│  │  Large Object│  │    Code Space       │   │
│  │    Space     │  │  (compiled code)    │   │
│  └──────────────┘  └────────────────────┘   │
└─────────────────────────────────────────────┘
```

- **Young generation**: Small, fast, collected often (Scavenge)
- **Old generation**: Large, collected infrequently (Mark-Sweep/Mark-Compact)
- **Large object space**: Objects exceeding a size threshold go directly here (skipping young generation)
- **Code space**: Where compiled machine code lives

You can inspect this layout at runtime:

```javascript
'use strict';

const v8 = require('node:v8');

const heapStats = v8.getHeapStatistics();

console.log('=== V8 Heap Statistics ===\n');
console.log(`Total heap size:      ${(heapStats.total_heap_size / 1024 / 1024).toFixed(2)} MB`);
console.log(`Used heap size:       ${(heapStats.used_heap_size / 1024 / 1024).toFixed(2)} MB`);
console.log(`Heap size limit:      ${(heapStats.heap_size_limit / 1024 / 1024).toFixed(0)} MB`);
console.log(`Malloced memory:      ${(heapStats.malloced_memory / 1024 / 1024).toFixed(2)} MB`);
console.log(`Peak malloced memory: ${(heapStats.peak_malloced_memory / 1024 / 1024).toFixed(2)} MB`);
console.log(`GC collections:       ${heapStats.number_of_native_contexts}`);

const heapSpaces = v8.getHeapSpaceStatistics();
console.log('\n=== Heap Spaces ===\n');
for (const space of heapSpaces) {
  console.log(`${space.space_name.padEnd(25)} ${(space.space_used_size / 1024).toFixed(0).padStart(8)} KB used / ${(space.space_size / 1024).toFixed(0).padStart(8)} KB total`);
}
```

## Key Takeaways

- V8 compiles JavaScript through a multi-tier pipeline: parsing to AST, Ignition bytecode for initial execution, TurboFan native code for hot functions
- Hidden classes enable fast property access — keep object shapes consistent by always initializing properties in the same order in constructors
- Inline caching makes repeated property access fast for monomorphic sites — avoid passing objects with different shapes to the same function
- Garbage collection uses two strategies: fast Scavenge for short-lived young objects, and slower Mark-Sweep/Mark-Compact for long-lived old objects
- Use `--trace-opt`, `--trace-deopt`, and `--trace-gc` flags to observe V8's decisions — they reveal why specific code patterns are fast or slow
